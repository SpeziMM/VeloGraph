How to read the complexity claims

V = visited graph nodes, E = examined edges, k = route points, I = search attempts and W = workers. Expected hash lookups are O(1), not a worst-case guarantee. KD-tree range queries can degrade to O(V). The heap search has Dijkstra-like operations but weighted heuristics and separate distance budgets do not provide exact A* optimality.

03 / Define a request

Choose a point—or an area.

This builds a runnable CLI command. It does not execute routing in your browser. Area mode tries the nearest eligible starts up to a limit; it does not search every possible point.

Search budget, reproducibility & graph input

Schematic only. Nearby nodes and distances here are not OSM data.


All CLI inputs and the exact route contract
    The selected graph node is both start and finish. A radius limits the start, not the whole route. The default coordinate snap limit is 250 m. Area mode sorts eligible nodes by approximate center distance then ID; eligibility only means an outgoing edge not classified motorway/trunk. Starts run sequentially; each start's attempts use CPU workers. Iterations are per start, so an area can cost up to candidates × iterations.
    Distance tolerance is a ranking preference, not a hard guarantee. Within each tolerance group, selection uses 0.6 × fitness + 0.4 × distance accuracy. Repeated roads and out-and-back sections are possible. Surface, scenery and slope are preferences; arbitrary must-visit points, polygon starts and GPX export are not implemented.

    Route data © OpenStreetMap contributors. Geometry view; no basemap requests.
    Output fields and limitations
    nodes preserves traversal order, including repeated nodes and closure. Each point contains id, lat, lon. stats contains total graph distance, fitness and score components. run contains seed, success, tolerance status, timings and start-selection metadata. A failure emits an empty points array; it does not prove impossibility. Coordinates are rounded on export, and straight segments do not reconstruct discarded road geometry.

    • Directed ring and one-way chain: closure and forward-edge validation.
    • Thread-count repeatability for fixed seeds; missing-edge scoring rejection.

    07 / Parallel hardware
    CPU workers today. GPU is unmeasured.
    

    The inspected Mac reports an Apple M5 Pro: 15 CPU cores, 16 GPU cores, 48 GB memory. Those counts are hardware inventory, not measured utilization.
    

    Shared graph
    read-only during search    →Serial precompute→Independent CPU attempts
    atomic queue · per-attempt RNG    →Ordered reduction
    

    What parallelism already exploits
    Independent attempts avoid shared mutation of their search state. The graph and precompute are shared read-only. Each attempt gets a deterministic RNG; results are reduced in index order. The calling thread participates, with no spawn for a one-worker run. Worker count is capped by the iteration count. Area starts are sequential to avoid nested worker pools.
    

    Why core count does not establish speedup
    Serial work, thread launch costs, unequal attempt sizes, hash lookups, priority queues and memory traffic may limit scaling. These are hypotheses based on the implementation, not profiler findings. More workers can be slower on small requests. Different core types and shared power budgets also mean “15 cores” is not a 15× speedup prediction.
    

    What a GPU experiment would need to establish
    The current pointer-heavy graph searches and per-attempt branching are not an existing Metal workload. Any GPU proposal needs an explicit kernel, suitable data layout and end-to-end measurements including dispatch/transfer overhead, plus unchanged validity and quality. No GPU acceleration or benefit is claimed here.
